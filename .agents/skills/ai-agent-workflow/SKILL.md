# AI智能体5级使用方法工作流（企业级增强版 v3.0）

## ⭐ 三条黄金法则

在使用任何AI工具执行任何任务之前，先记住这三条法则——它们决定了AI输出的质量上限：

> **法则一：项目理解优先（Understand the Project First）**
> AI最大的失败不是写错代码，而是写了"正确但无关"的代码。动手前必须让AI理解：这个项目为什么存在、为谁服务、约束是什么。**代码服务于业务，而不是反过来。**

> **法则二：上下文即燃料（Context is Fuel）**
> AI输出质量 = f(上下文质量)。模型能力已经过剩，缺的永远是你没给的信息。一次高质量交付所需要的信息，应该在任务开始前就注入，而不是在返工中逐渐补齐。

> **法则三：先澄清再执行，输出必自审（Clarify Before Acting, Review Before Delivering）**
> 严禁在需求模糊时直接动手。AI必须先复述理解、列出假设、提出澄清问题；交付前必须对照检查清单自我审查。**返工十次，不如澄清一次。**

## 第0步：项目认知注入（大型项目必做）

**这是本技能区别于普通工作流的核心：在执行任何任务前，先建立项目认知。**

### 0.1 项目认知文件体系（Project Brief System）

在项目根目录维护以下四个文件（模板见 `references/project-brief-template.md`）：

| 文件 | 内容 | 更新频率 |
|---|---|---|
| **PROJECT_BRIEF.md** | 项目一句话定位、业务目标、目标用户、核心价值 | 需求变化时 |
| **ARCHITECTURE.md** | 技术栈、分层结构、模块清单、关键依赖、数据流 | 架构变更时 |
| **CONVENTIONS.md** | 编码规范、目录约定、命名规则、禁止事项 | 团队约定变化时 |
| **GLOSSARY.md** | 领域术语表（统一"订单/工单"这类术语的精确定义） | 新概念出现时 |

**为什么重要：** 大项目中AI翻车的第一原因就是不知道"支付"在你们项目里叫"结算"，不知道"用户"和"会员"是两个概念。术语表能直接消灭这类错位。

### 0.2 让AI理解项目的方法（按优先级）

1. **喂认知文件**：把上述文件直接贴给AI（或用工具自动生成，见 `scripts/tools/context_builder.py`）
2. **喂结构**：给出目录树 + 每个核心目录一句话职责说明
3. **喂样例**：给1-2个"项目里写得最好的"文件作为风格锚点
4. **喂历史**：最近5条相关的Git commit message，让AI理解演变脉络

### 0.3 30秒项目认知检查

每次开始任务前，AI应能回答以下问题。答不上来说明上下文不足，先补齐再动手：

- [ ] 这个项目是做什么的？为谁解决什么问题？
- [ ] 本次任务在整体架构中的位置是什么？
- [ ] 有哪些必须遵守的现有约定？
- [ ] 本次修改会影响哪些上下游模块？

## 需求澄清协议（Clarify Protocol）

**借鉴自广受好评的"惊艳提示词"理念：先理解再行动。** 当需求描述超过一句话，或涉及多文件修改时，AI必须执行以下四步：

### 步骤1：复述理解（Restate）
> "我理解你要做的是：……。我的理解对吗？"

### 步骤2：列出假设（Assumptions）
> "在开始前，我做了以下假设：1. ……；2. ……。如有不符请指出。"

### 步骤3：提出澄清问题（Clarifying Questions）
> "开始前我需要确认3个问题：1. ……；2. ……；3. ……。"

**澄清问题的优先级：** 影响架构的问题 > 影响接口的问题 > 影响实现细节的问题。一次问完，不要挤牙膏。

### 步骤4：方案先行（Plan First）
> "基于以上理解，我的实施计划是：步骤1 → 步骤2 → 步骤3。预计修改X个文件。确认后我开始执行。"

**执行规则：**
- 需求明确且是单文件小改动 → 可跳过步骤1-3，直接执行
- 需求模糊、多文件、有架构影响 → 必须完整走完四步
- 用户说"直接做" → 尊重用户，但交付前仍必须自审（见七步工作流第6步）

## 一、5级使用框架

### 第1级：基础代码生成
**适用场景：** 快速原型、小功能开发 | **复杂度：** 低

**使用方法：** 给出明确的函数签名和功能描述，指定输入输出格式，说明边界条件。

**提示词模板：**
```
请用[编程语言]编写一个[功能描述]的函数/类。

要求：
- 输入：[输入参数和类型]
- 输出：[返回值和类型]
- 边界条件：[特殊情况处理]
- 代码风格：[遵循的规范]
```

---

### 第2级：代码理解与修改
**适用场景：** 维护已有项目、技术债务清理 | **复杂度：** 中

**使用方法：** 提供完整代码上下文，说明修改位置和期望效果。**修改前先让AI复述这段代码当前的行为，确认理解一致后再改。**

**提示词模板：**
```
请先说明以下代码当前的完整行为（包括边界情况），然后[重构/优化/修复]：

[粘贴代码]

需要修改的地方：
1. [问题1]
2. [问题2]

期望效果：
- [效果1]

约束条件：
- [保持向后兼容 / 不改变公共API / ...]
```

---

### 第3级：多文件项目工作
**适用场景：** 中等规模功能开发 | **复杂度：** 中高

**使用方法：** 描述项目架构和模块职责，明确模块间接口。**先让AI输出修改方案（改哪些文件、每个文件改什么），确认后再执行。**

**提示词模板：**
```
项目架构：
- [文件/模块1] - [职责]
- [文件/模块2] - [职责]

请实现[功能名称]，要求：
1. 在[模块1]中实现[具体功能]
2. 在[模块2]中添加[具体逻辑]
3. 编写对应的测试用例

执行前请先输出你的修改方案（文件清单+每个文件的改动点），确认后再动手。

技术约束：
- [框架/库要求]
- [代码规范要求]
```

---

### 第4级：复杂架构设计
**适用场景：** 大型系统重构、架构升级 | **复杂度：** 高

**使用方法：** 描述现有系统、问题和约束，让AI给出多个可选方案并对比权衡，最后落成ADR（架构决策记录）。

**提示词模板：**
```
现有系统问题：
1. [问题1] - [影响和量化数据]

优化目标：
- 性能：[具体指标]
- 可用性：[具体指标]

约束条件：
- 技术栈：[现有技术]
- 资源：[人力/时间/预算]

请提供：
1. 至少2个可选方案，每个方案包含：架构说明、优缺点、迁移成本、风险
2. 你的推荐方案和理由
3. 实施步骤（可分阶段、可回滚的）
4. 需要沉淀为ADR的决策点清单
```

---

### 第5级：自主项目管理
**适用场景：** 端到端功能交付 | **复杂度：** 极高

**使用方法：** 描述完整业务需求、技术约束和验收标准。**必须先产出任务分解文档并获得确认，再进入执行。**

**提示词模板：**
```
业务需求：[完整需求描述]

技术约束：
- 框架：[技术框架]
- 数据库：[数据库类型]
- 部署：[部署要求]

验收标准：
1. [功能验收标准]
2. [性能验收标准]

请先不要写代码，按以下顺序产出：
1. 需求复述和澄清问题（Clarify Protocol）
2. 技术方案设计
3. 任务分解（每个任务：目标、输入输出、依赖关系、预计工作量、验收标准）
4. 风险清单

待我确认任务分解后，再按任务逐个执行。每完成一个任务，更新任务状态并汇报。
```

**第5级任务分解示例：**
```
┌─ 阶段1：地基 ────────────────┐
│ T1 数据库设计 → T2 数据模型 → T3 数据访问层 │
└──────────────────────────────┘
              ↓
┌─ 阶段2：核心 ────────────────┐
│ T4 业务服务层 → T5 API接口 → T6 单元测试    │
└──────────────────────────────┘
              ↓
┌─ 阶段3：交付 ────────────────┐
│ T7 集成测试 → T8 文档 → T9 部署验证        │
└──────────────────────────────┘
```

## 二、七步核心工作流

在原有5步基础上升级为7步，新增"项目认知加载"和"自我审查"两个关键环节：

```
步骤1：项目认知加载（大项目必做，小任务可跳过）
   ↓ 加载 PROJECT_BRIEF / ARCHITECTURE / CONVENTIONS / GLOSSARY
步骤2：需求澄清（Clarify Protocol）
   ↓ 复述 → 假设 → 澄清问题 → 方案先行
步骤3：方案规划
   ↓ 复杂任务先输出计划，确认后执行（思维链）
步骤4：上下文注入
   ↓ 一次性给足：相关代码 + 约束 + 样例 + 术语
步骤5：分阶段执行
   ↓ 核心逻辑 → 错误处理 → 边界条件 → 性能 → 美化
步骤6：自我审查（Self-Review）★新增
   ↓ 交付前AI对照检查清单自审
步骤7：迭代优化与知识沉淀 ★新增
   ↓ 根据反馈修正；把踩过的坑记入经验库
```

### 步骤6：自我审查清单（AI交付前必须自问）

```
□ 需求覆盖：每个需求点都有对应实现吗？
□ 假设检查：我做的假设都成立吗？有没有悄悄换了需求？
□ 边界完整：空输入/超长输入/并发/异常路径都处理了吗？
□ 约束遵守：命名、分层、依赖方向符合项目约定吗？
□ 一致性：和项目现有代码风格、错误处理方式一致吗？
□ 测试配套：核心逻辑有测试吗？测试能真的跑通吗？
□ 影响面：有没有我没想到但会被影响的地方？
```

**自审输出格式：**
> "自审完成。已确认：需求1、2已覆盖，边界条件已处理。
> 遗留风险：X场景未覆盖（原因：……），建议后续补充。
> 需要你重点检查：[文件A的第N行逻辑]。"

### 步骤7：知识沉淀

每次任务结束后，判断是否有值得记录的内容：

- 踩坑了 → 记入项目 `docs/lessons-learned.md`（现象、根因、解法）
- 做了架构/技术选型决策 → 记入ADR（见 `references/adr-template.md`）
- 发现新术语或术语定义有误 → 更新 `GLOSSARY.md`
- 提示词效果不好 → 修正后存入个人提示词库

**积累的价值：** 40个任务之后，你的提示词库和经验库会拉开数量级的差距——这就是"18天跑400个任务"实践者真正的复利所在。

## 三、企业级项目模式

### 3.1 分层上下文（L0-L2）

大项目的上下文不能一股脑全塞给AI，按需分层加载：

| 层级 | 内容 | 何时加载 |
|---|---|---|
| **L0 全局层** | PROJECT_BRIEF + ARCHITECTURE 摘要 + CONVENTIONS | 每个任务开始 |
| **L1 模块层** | 所涉模块的职责、接口定义、依赖关系 | 涉及该模块的任务 |
| **L2 文件层** | 具体文件内容、相关测试、上下游调用方 | 编码执行时 |

**加载原则：** 宁可多给L1，不要漏给L0；L2只给相关的，不要整库贴入。

### 3.2 架构决策记录（ADR）

企业级项目每做一个不可逆或高成本的技术决策，都应沉淀ADR：

```
# ADR-007: 订单服务消息推送采用Outbox模式

## 状态：已接受
## 背景：双写数据库和MQ时出现过数据不一致
## 决策：使用事务性Outbox模式，本地表+轮询投递
## 备选方案：直接双写（否决：一致性风险）/ Seata（否决：引入过重）
## 后果：需要新增outbox表和投递任务；排障时先查outbox表
```

完整模板见 `references/adr-template.md`。

### 3.3 质量门禁（Quality Gates）

企业级任务交付前必须通过的门禁，可配合 `scripts/tools/code_quality_checker.py` 和 `automated_tester.py` 自动化：

| 门禁 | 标准 | 工具 |
|---|---|---|
| 静态检查 | 无error级问题 | code_quality_checker.py |
| 安全扫描 | 无高危漏洞 | code_quality_checker.py |
| 单元测试 | 核心逻辑全覆盖、全部通过 | automated_tester.py |
| 自我审查 | 七步工作流步骤6全部通过 | AI自审 |
| 影响面确认 | 上下游模块负责人知情 | 人工 |

### 3.4 遗留系统改造守则

改造遗留系统时，额外遵守：

1. **先读后改**：改动前先让AI完整解释现有代码的行为，确认理解一致
2. **测试先行**：先给要改的代码补 characterization test（刻画现状的测试），再动手
3. **小步提交**：每个可独立验证的改动单独提交，随时可回滚
4. **不顺手修**：发现无关问题记录下来，不要混入本次改动扩大影响面

## 四、提示词核心原则

融合"惊艳提示词"类内容反复验证有效的方法论：

### 4.1 角色设定（Role Priming）
> "你是一名拥有15年经验的[领域]专家，特别擅长[具体能力]。"

给AI一个具体、有约束的角色，比"帮我写代码"能显著提升输出专业度。角色要具体到领域和场景，不要空泛。

### 4.2 先理解再行动（Understand First）
见上文《需求澄清协议》。这是所有"惊艳提示词"的共同内核：**让AI先证明它理解对了，再允许它动手。**

### 4.3 思维链规划（Plan Before Execute）
> "先不要写代码。先输出：1. 你对这个任务的分析；2. 实施计划；3. 你预计会遇到的坑。我确认后你再开始。"

强制AI先展示思考过程，可以在写第一行代码之前拦截90%的方向性错误。

### 4.4 精确约束胜过冗长描述（Precision over Length）
```
❌ 模糊：帮我写个登录接口
❌ 冗长但无约束：帮我写一个支持各种情况的登录接口，要好用，要稳定……
✅ 精确：实现POST /api/auth/login：
   - 入参：{email, password}，格式校验失败返回400
   - 密码错误：统一返回"账号或密码错误"（防用户枚举），连续5次失败锁定30分钟
   - 成功：返回access_token(2h) + refresh_token(7d)，bcrypt校验
   - 依赖：复用 services/auth.py 现有的 verify_password()
```

约束越具体，AI的自由度越收敛，输出越接近预期。**好的提示词是约束的艺术，不是形容的堆砌。**

### 4.5 输出格式约定（Output Contract）
复杂输出前，先约定格式：
> "输出格式：1. 修改文件清单（表格）；2. 每个文件的关键改动说明；3. 自审结果；4. 遗留风险。"

### 4.6 少数派但重要的技巧

- **要求AI说"不知道"**："如果信息不足，直接告诉我缺什么，不要编造。"
- **给反例**："不要使用单例模式，不要引入新依赖。"
- **锚定样式**："参考 src/services/order_service.py 的风格。"（一个好样例胜过十条规范）
- **控制篇幅**："核心逻辑不超过50行/函数，先给骨架再填肉。"

## 五、工具适配速查

详细适配指南（含20+工具的完整示例）见 `references/tool-adaptation.md`。

| 工具类型 | 代表工具 | 上下文方式 | 最佳任务级别 |
|---|---|---|---|
| 云端智能体 | Codex, Devin, OpenHands | `#file`/仓库链接 | 第3-5级 |
| IDE集成 | Cursor, Copilot, Windsurf | `@`/自动感知 | 第1-3级 |
| 对话式AI | Claude, GPT-4, Gemini | 上传/粘贴 | 第1-4级 |
| 命令行 | Aider | Git集成 | 第2-4级 |
| 本地/开源 | DeepSeek Coder, Tabby | 本地项目 | 第1-2级 |

**通用上下文注入格式（任何工具通用）：**
```
【项目认知】[PROJECT_BRIEF.md 一句话 + 相关约定]
```

## 七、常见反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 不给上下文直接说"帮我实现XX" | AI凭通用经验猜测，产出"正确但不符合本项目"的代码 | 至少给L0层认知 + 相关代码 |
| 一次甩一个巨大模糊的需求 | 方向性错误，全部返工 | Clarify Protocol + 任务分解 |
| AI输出直接采纳，不看 | 埋入安全漏洞、风格不一致 | 自审 + 质量门禁 |
| 让AI"优化一下代码"却不给约束 | 改出花但破坏向后兼容 | 明确约束：API不变、性能目标 |
| 决策不记录，全靠人脑记忆 | 三个月后没人知道当初为什么这么设计 | 沉淀ADR |
| 踩坑后不复盘 | 同样的坑反复踩 | 记入 lessons-learned |

## 八、总结

### 核心心法
1. **理解先于编码**：项目认知注入 + 需求澄清协议
2. **上下文决定上限**：分层加载，一次给足
3. **计划先于执行**：思维链规划，确认后动手
4. **自审先于交付**：自我审查清单 + 质量门禁
5. **沉淀大于完成**：ADR + 经验库 + 提示词库的复利

### 成功关键
- 第1-2级任务：走精简流程（明确需求 → 执行 → 自审）
- 第3-5级任务：走完整七步流程
- 企业级项目：第0步认知注入 + 分层上下文 + ADR，一个都不能少
