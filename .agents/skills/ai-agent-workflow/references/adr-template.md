# 架构决策记录模板（ADR Template）

> ADR（Architecture Decision Record）用于记录**不可逆或高成本的技术决策**，让三个月后的你（和AI）知道"当初为什么这么设计"。
>
> **何时需要ADR：** 技术选型、架构模式变更、数据库结构调整、引入新依赖、放弃某个方案。
> **何时不需要：** 普通代码实现细节、可轻易回滚的小改动。
>
> 存放位置：`docs/adr/ADR-XXX-标题.md`，编号递增。

---

## 模板正文

```markdown
# ADR-[编号]: [决策标题，用一句话说清决策内容]

- **状态：** [提议 / 已接受 / 已废弃(被ADR-XXX取代) / 已否决]
- **日期：** [YYYY-MM-DD]
- **决策人：** [姓名/角色]
- **关联：** [相关Issue/PR/其他ADR编号]

## 1. 背景与问题（Context）

[为什么需要做这个决策？遇到了什么问题？
- 现状描述：[当前是怎么做的]
- 触发因素：[什么事件迫使决策，如：并发量增长后频繁出现数据不一致]
- 量化数据：[有时间线/数据更好，如：双写不一致周均3次]）

## 2. 决策内容（Decision）

[我们决定：用一句话说清最终方案，然后展开关键设计]

## 3. 备选方案与权衡（Options）

### 方案A：[名称]（✅ 已采纳）
- 优点：[...]
- 缺点：[...]
- 迁移/实施成本：[...]

### 方案B：[名称]（❌ 否决）
- 优点：[...]
- 否决原因：[...]  ← 这句最重要，防止后人重蹈覆辙

## 4. 后果（Consequences）

### 正面影响
- [...]

### 负面影响（诚实记录）
- [如：新增一张outbox表，写入路径多一次DB操作]

### 需要遵守的新约定
- [如：所有需要投递MQ的业务操作，必须在同一事务内写outbox表]

### 回滚预案
- [如：投递任务保留开关，可一键切回同步直投]

## 5. 验证标准（How to Verify）

- [如何确认这个决策达到了预期，如：上线后观察4周，双写不一致应为0次]
```

## 给AI使用的提示词模板

让AI参与ADR撰写时使用：

```
请基于以下信息撰写一份ADR：

背景：[问题描述]
候选方案：[方案1、方案2、...]
团队倾向：[如果有]
约束：[技术栈/资源/时间]

要求：
1. 按 ADR 标准结构输出（状态/背景/决策/备选方案权衡/后果/验证标准）
2. 备选方案必须给出明确的否决理由
3. 后果部分必须诚实列出负面影响，不要只说好话
4. 如果信息不足，先列出澄清问题再写（Clarify Protocol）
```

---

## 优秀ADR的三个标准

1. **否决理由比采纳理由更有价值** —— 它防止团队（和AI）在半年后重新提出已被否决的方案
2. **诚实记录负面影响** —— 只写好处的ADR没有可信度
3. **有验证标准** —— 决策不是终点，"有效"才是
